Approach · Protocol II

A Stronger Guarantee

Protocol I's limitation: what breaks under stress. Protocol II addresses this with a different trade-off.

Protocol IProtocol II
Reader behaviorSnapshot → Read → ValidateDirect read, zero overhead
Writer behaviorLock + increment versionLocal lock + atomic ops
Code changeMinimalRequires internal changes
Under contentionDegradesStays flat

Core Trade-off

In Protocol II, writers take on the burden of ensuring reader consistency. Instead of detecting conflicts (Protocol I), writers prevent them.

Comparison to Lock-Free

Easier than full lock-free because writers can use locks (just not against readers). More leverage than CAS-only designs.

Best For: Read-heavy workloads under high contention. When readers must never wait.

Approach · Implementation

Making the Data Structure Safe

Local Modifications: Atomic Everywhere

All fields visible to readers must be std::atomic. On x86, atomic loads add zero extra instructions — only prevent compiler reordering.

Structural Changes (N-step protocol)

  1. Acquire necessary locks (node + parent)
  2. Prepare new version off-critical-path
  3. Atomic pointer swing to install
  4. Mark old version obsolete, release locks

Tricky Case: Multi-step Operations

When a structural change can't be done atomically, readers may see intermediate states. Solution: add an immutable field (set at creation time) readers can use to self-correct.

Implementation Detail

Pack related fields into a single machine word to enable one atomic store. Trade-off: slightly reduced capacity for stronger consistency.

Conclusions

The Takeaway

① Protocol I

Key technique. Minimal code change (~NN lines). Near-optimal scalability when conflicts are rare. Use by default.

② Protocol II

Readers never block. Writers use local locks + atomics. Worth the extra code when reads must never wait.

③ General Principle

Not specific to one data structure. Apply to B-trees, search trees, hash tables. Pragmatic middle ground between locking and lock-free.

The real enemy isn't X — it's Y. Both protocols eliminate Y for readers. Pick Protocol I for simplicity, Protocol II when reads must never wait. Don't abandon X — use it sparingly and deliberately.
